Run `payload generate:importmap` after you add, move, rename, or remove a custom admin component path
and need to refresh Payload's generated admin imports. From a pnpm project, the direct command is:

<RunnableCommand
  command="pnpm payload generate:importmap"
  label="Copy the Payload generate import map command"
/>

The command rebuilds the file Payload uses to connect component path strings in `payload.config.ts`
to real modules in the admin bundle. It does not regenerate your collection and block types. Run
`payload generate:types` separately when the data schema changes.

That distinction is the shortest route through most import-map problems: the import map describes
admin modules, while generated types describe document data. A block or plugin change can require
one command, the other, or both.

## What `payload generate:importmap` generates

Payload custom components are configured by path instead of being imported directly into
`payload.config.ts`. A field component might look like this:

```ts
import { buildConfig } from 'payload'

export default buildConfig({
  admin: {
    components: {
      logout: {
        Button: '/components/LogoutButton#LogoutButton',
      },
    },
  },
})
```

Payload's [custom components documentation](https://payloadcms.com/docs/custom-components/overview)
explains why: keeping component references as paths leaves the server-side config lightweight and
Node-compatible. The admin build still needs concrete imports, so Payload generates a lookup from
each configured path to its module and export.

The default output is one of these files, depending on whether your project uses a `src` directory:

```text
src/app/(payload)/admin/importMap.js
app/(payload)/admin/importMap.js
```

You can override that location with `admin.importMap.importMapFile`. You can also set
`admin.importMap.baseDir` when your component paths should resolve from a directory other than the
project root. Both options belong in the Payload config, not in the generated file.

## The direct command and the package script

Use the direct Payload CLI command when you want an instruction that does not depend on a repository
script:

```bash
npx payload generate:importmap
```

With pnpm, the equivalent direct invocation is:

```bash
pnpm payload generate:importmap
```

Many Payload starters expose the same command through `package.json`:

```json
{
  "scripts": {
    "generate:importmap": "payload generate:importmap"
  }
}
```

Then the shorter project script works:

```bash
pnpm generate:importmap
```

The package script is a repository convention, not a different generator. If `pnpm
generate:importmap` says the script is missing, use the direct command or add the script shown above.
Payload's [community answer to this question](https://payloadcms.com/community-help/discord/whats-the-right-way-to-manage-importmapjs-is-there-a-tool-to-auto-update-or-regenerate-that)
makes the same distinction.

## When you need to run it manually

Current Payload v3 documentation says the import map is regenerated at application startup, during
Hot Module Replacement, and when you run the command manually. That automation covers ordinary
local editing, but manual generation remains useful when:

- you changed component paths without a dev server running;
- you are preparing a clean production build or CI job;
- a branch switch left the generated file behind the config;
- your project tracks generated output and review should show the exact diff;
- you are debugging whether Payload can load the intended config;
- an installer or plugin added custom components outside the current dev session.

The file is generated at startup or build time, not continuously during normal production runtime.
If you ignore the generated file in Git, make generation a dependable build prerequisite. If you
commit it, regenerate before review and check that only expected component entries changed.

## Import map versus generated types

The two generators answer different questions:

| Change | Run `generate:importmap` | Run `generate:types` |
| --- | --- | --- |
| Add or move a custom admin component path | Yes | Only if the schema also changed |
| Change a component's named export | Yes | No |
| Add, remove, or rename a collection field | No | Yes |
| Add a block to a Blocks field | If it adds an admin component path | Yes |
| Rename a block field and its admin field component | Yes | Yes |

Payload's [type generation guide](https://payloadcms.com/docs/typescript/generating-types) explains
how `generate:types` turns the active config into TypeScript definitions. For a Blocks field, the
generated Page type contains union members distinguished by `blockType`. The import map does not
contain those data interfaces.

If the admin loads the new component but TypeScript rejects a new block field, regenerate types. If
the frontend typechecks but the admin cannot resolve a custom component, regenerate the import map.
If both sides are stale, confirm the collection and component paths are registered in the config
before running both commands.

## Fix a stale or broken import map

Start with the path in `payload.config.ts`, not the generated file. These checks catch the common
causes in the order that is cheapest to verify.

### 1. Confirm the path and export

Component paths resolve from the project root unless `admin.importMap.baseDir` changes that rule. A
named export needs `#ExportName` in the path or an explicit `exportName` property. A default export
does not.

Check capitalization too. A path can appear to work on a case-insensitive local filesystem and then
fail in Linux CI or production.

### 2. Confirm the generator loads the same config

Run the command from the project root and with the environment the application expects. If the
project has more than one Payload config or uses environment-dependent imports, a successful command
can still generate from the wrong source.

### 3. Regenerate, then inspect the entry

Run the direct command and search the output for the configured component path. The generated import
should point to the file and export you just checked. Do not repair a wrong generated entry by hand;
the next generation will overwrite it.

### 4. Restart the process that owns the module graph

If the generated file is correct but the admin still shows the old component, restart the dev server
or rebuild from a clean application cache. Regeneration updates the source file. A running process
can still retain an older module graph.

### 5. Check Payload package versions

Keep `payload`, `@payloadcms/next`, and `@payloadcms/ui` on compatible versions through the lockfile.
Unexpected generator behavior after an upgrade is easier to diagnose when the relevant package
versions are visible in the same change.

The broader [Payload block not rendering checklist](/blog/payload-block-not-rendering) separates
import-map failures from missing saved data, renderer mappings, and stale generated types.

## Make generation reproducible

Decide whether generated artifacts enter version control, then make the opposite environment prove
itself:

- If you commit `importMap.js`, run generation in CI and fail when `git diff` is nonempty.
- If you ignore it, run generation before the production build in every clean environment.
- Pin Node, the package manager, and Payload packages so local and CI output agree.
- Keep `payload.config.ts` free of browser-only imports that the Node-side generator cannot load.
- Review import-map churn. A one-component change should not silently rewrite unrelated paths.

This workflow turns a stale file from a production surprise into a small, reviewable diff.

## How Payload Components handles the command

Payload Components treats source delivery and generation as separate installation stages. A block
manifest declares `generate:types` and `generate:importmap` as post-install work. The CLI copies the
source, registers the block in the Pages collection, maps its renderer, and then runs the target
project's scripts against the final config.

It does not copy a foreign `payload-types.ts` or `importMap.js` into your project. Those generated
artifacts depend on your own config, component paths, and output conventions. The
[installation guide](/docs/installation) shows the complete supported flow, while
[Anatomy of an install](/blog/anatomy-of-an-install) explains why generation runs only after the
wiring changes land.

Try the complete workflow on a branch:

<RunnableCommand
  command="npx payload-components add hero-basic --dry-run"
  label="Copy the Payload Components dry-run command"
/>

The dry run lists the files, collection registration, renderer mapping, dependencies, and generation
commands without changing the project. Remove `--dry-run` when the plan matches your repository.

After installation, inspect the generated entries, typecheck, build, and open the admin. If a
supported starter produces unstable output, include the command, Payload versions, sanitized paths,
and generated diff in a report to the [open registry](/docs/registry). That evidence makes a
generator problem reproducible instead of leaving it as an admin-only symptom.
